# appview-rs lane av25: grouped notifications, live unread badge, filled heart

Date: 2026-10-29

## Completed

- Removed the symbol-level `fill="none"` attribute from every SVG symbol. The default outline fill now lives in `.icon { fill: none; }`; the existing liked-post and liked-thread rules can fill the heart. The stylesheet URL is now `app.css?v=m6`, and the script URL is `app.js?v=js5`.
- Grouped likes by post, reposts by post, and follows when events are within 48 hours and share the same read state. Replies, mentions, and quotes remain individual rows. Group rows show the event icon, up to five hydrated avatars in newest-first order, the newest actor name, the correct singular/plural count, a short age, and a two-line subject-post preview for likes and reposts. Existing profile hydration still uses the 1.5 second page budget and its current fallbacks.
- Group pagination uses a cursor at the newest event of each complete group. The page groups the viewer's notification history before slicing, so events in a group cannot reappear on a later page or get dropped at a page boundary. This currently materializes that viewer's notification history in memory per page request; cost is proportional to that viewer's stored notification count.
- Added the `notification_last_seen` SQLite table. `/notifications` records the viewer's current time, and unread counts include only events newer than that timestamp. The web badge is server-rendered on desktop and mobile navigation, displays `9+` above nine, and is hidden at zero. The XRPC unread-count endpoint uses the same stored boundary.
- Added logged-in, same-origin `/notifications/stream` and `/notifications/unread-count` endpoints. Ingest publishes updated counts through a bounded in-process broadcast; each stream sends an initial count and a heartbeat every 25 seconds. A viewer can hold at most four streams. Browser JavaScript updates both badges from SSE, falls back to a JSON count request every 30 seconds on stream errors, and refreshes when the page becomes visible.

## Stream resource estimate

Each SSE stream holds a broadcast receiver, heartbeat timer, viewer identifiers, and a small guard: a few hundred bytes of Rust bookkeeping per stream, plus string allocations and the HTTP/runtime/TLS/socket buffers. There is one bounded 16-count broadcast channel per viewer with active streams (128 bytes of raw `usize` payload capacity, plus channel metadata), shared by that viewer's tabs. A notification update queries the new count once per affected viewer and fans it out only to that viewer's open streams, capped at four recipients. Closed subscriptions remove their channel; there is no database polling loop for SSE.
